# 连续预览修复：提前备帧与实际消费同步

原来“声音继续走、画面一直等待”的问题已在原海南 QA 工程取得修复证据。现在先准备后面的画面，到声音真正播放到对应位置时再显示；准备不足时先跳过部分预览采样，仍赶不上则声画一起等待。导出帧率不变。

这不是全程无停顿的性能验收。海南工程仍有短暂缓冲，本轮最长约 **672 ms**；后续需要减少跨素材切换的冷读取开销。

## 实现范围

- 扩展现有 `visual.preview.frame` 类型契约：允许提前最多 1 秒准备，Rust 返回下一采样时间；正常呈现仍受原 150 ms 同步门槛约束。
- 队列最多 8 张，呈现和排队画面最多占 64 MiB。原生端先从原 RGBA/GPU 额度扣除驻留画面，再生成解码额度，避免两边预算不一致。
- 画面只跟随 AudioWorklet 的实际消费。声音最多领先已显示画面 100 ms；等待期间不消耗 PCM、不推进时间线，恢复后接着消费原样本。
- 保留现有 Mediabunny、Classic GPU、固定修订与授权资源接口。关闭缓存时先结束解码迭代器，再关闭素材连接；并发清理共用同一次关闭。
- 修正验收观察器在恢复播放后误选旧 Worker 的问题，读取最新 Worker 的实际 PCM 和控制记录。

## 实际验证

固定 Native 为 `d23a944a`，Web 和执行器的完整身份见 [JSON 记录](buffered-scene-playback-20261021.json)。服务、原素材和两个既有工程均复用，没有重新导入或导出视频。

| 检查 | 结果 |
|---|---|
| 8 秒红绿测试视频 | 191 个推进画面，播放到末尾，零缓冲量子 |
| 独立像素与声音 | 7 次红绿取样通过；440 Hz 实测 439.999916 Hz，RMS 0.088316 |
| 测试视频声画偏差 | 0–2.34 ms，首画 657 ms |
| 海南首次播放 | 522 个画面，推进至约 25 秒，最大呈现偏差 60 ms |
| 暂停与跳转 | 暂停后时钟保持，设备关闭；跳转准确到 6.5 秒 |
| 海南恢复播放 | 759 个画面，实际消费 35.5 秒 PCM，到达 42 秒片尾，设备关闭，零页面异常 |
| 工程数据 | 48 工程、912 修订、864 事务、262 任务的完整行哈希均与本轮前一致 |
| 自动检查 | Web 100、执行器 170、Rust 画面/预算/绑定 12 项通过；架构、边界、生成契约、canonical、SDK 和 Web 构建通过 |

初始海南窗口消费 25.07 秒 PCM，另有约 2.39 秒缓冲；恢复窗口消费 35.5 秒 PCM，另有约 4.92 秒缓冲。等待时保持同步，不把静音等待算成真实声音消费，也不把完成播放等同于持续 25 fps。

此前一次长恢复播放在约 24 秒失败，并出现素材连接已关闭异常。新增的清理顺序测试在修改前失败、修改后通过；修正后重跑原完整路径通过。该证据不代表所有资源生命周期问题均已排除。

已有音频窗口/驻留 Application 测试失败仍保留；本轮未宣称全 Rust 工作区通过。物理听审、大素材、长源、跨平台、完整视频输出与 S1/A7/D8 验收继续开放。
