# 画面等待提示与后台执行 · 2026-10-22

本轮修复用户反馈的逐帧“正在等待同步画面”。实现范围是[连续预览方案](../architecture/continuous-preview-plan.md)阶段 2 的呈现调度和执行隔离；540p 实际执行、复杂段缓存及持续高清帧率仍未完成。

## 原因和实现

旧代码在有效画面落后输出位置超过 150 ms 时清空画布，下一帧恢复后又重复清空，造成播放与等待提示交替。现在同一修订、同一代次的有效画面可以保持，直到最新可显示画面到达。跳转、新代次、切换修订、授权失败和关闭仍立即失效旧内容。新到但已落后 125 ms 的画面继续丢弃，保持旧画面不等于新画面已经通过同步验收。

开始播放前同步准备首帧；输出时钟建立后，在 requestAnimationFrame 中按最新输出位置选帧。一个屏幕刷新周期内的设备回执、原生报告和渲染完成合并一次，只显示最新到期画面，不提前显示未来帧。关闭时取消排定回调。保持原位图只占原有显示内存，淘汰的队列位图立即关闭；计数只在真实换帧时增加，保持画面不伪算帧率。

第一轮实际播放证实，仅取消清空会留下严重停帧，因此没有将其记成完整修复。之后把原有 VisualPreviewRenderer 的解码、字体、Rust RPC／绑定和 WebGPU 合成整体移入一个独立 Worker，完成的 ImageBitmap 转交界面显示。每个执行器只允许一个进行中的请求，没有另建工程解释器、播放器或原生操作。连接、固定修订、场景、owner／lease／generation／overlay 身份继续原样传递，所有授权和绑定仍由原 Rust 操作检查。

Worker 私有协议由已有 SDK 与执行器参数／返回类型派生，不复制公共 DTO；无新 crate、依赖或架构例外。取消区分帧取消与变换手势意图取消，保留原有异步编译退出语义。原生拒绝的错误类型／代码和诊断跨线程保留，不能把撤权吞成普通迟到。关闭拒绝在途请求、释放迟到位图，并对线程退出设置有界兜底。

图片在没有 HTMLImageElement 的 Worker 中使用同一已校验 PNG／JPEG 字节，通过 createImageBitmap 解码并在完成／取消时释放位图。视频、字体、蒙版与效果继续复用现有执行器。准备提前量改用完整请求耗时，包含后台执行、消息传递和界面调度；快速一帧仅让提前量渐降，避免反复低估。原生 1 秒准备许可、最高 800 ms 客户端提前量和资源上限没有扩大。

## 不通过的性能范围

Worker 显著降低了一些热帧的等待：部分热帧准备约 40–100 ms，短合成样例记录约 23 ms；冷启动和复杂段仍慢，不能用局部热帧代表整体。最终海南实播最后观测到 92 次真实换帧、31 次已准备但丢弃的画面；还存在没能及时准备的源帧，不能用这些计数计算完整漏帧率。最大观测画面落后 **5.389333 秒**，仍远超同步目标。因此本轮只关闭反复清黑／提示闪烁和主线程执行耦合，**不关闭持续高清播放或音画同步性能验收**。原前景线程仅保持画面时的 12 次换帧、Worker 首轮及最终实播分别保留原记录，不重新标记失败候选为成功。

输出时钟未改；实播中仍有声音缓冲观测，未声明每量子无耗尽或物理听审通过。原 125／150 ms 新帧准入保持，旧画面保持的真实时间和换帧计数公开在 DOM 观测，绝不把保持当同步成功。后续优先实施原生控制的 540p 执行档，再根据测量接入有界代理／复杂片段缓存；不通过 CSS 缩小画面假称降低执行分辨率。
