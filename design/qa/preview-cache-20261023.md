# 540p、合成缓存与连续呈现 · 2026-10-23

本轮完成原生 540p 执行、两秒合成结果缓存和独立线程中的画面呈现，解决已有海南工程在预备完成后的画面落后、停帧和反复等待。范围及候选见[结构化验收](preview-cache-20261023.json)；不是全工程、全设备或物理音画同步验收。

## 实现与原因

原先即使将解码／合成移入 Worker，高清复杂画面仍然算不过来；页面主线程还承担最终绘制及逐帧 React 更新。只保持旧画面、增大队列或统一时间值均不能解决这些耗时。

Rust 现在在原逻辑画布求值后生成实际最高 960×540 的预览栅格，保留宽高比、偶数尺寸并避免放大小工程。字幕、变换、蒙版、模糊与相关像素参数按共享投影执行；暂停仍准备原分辨率。实际海南缓存是 960×540，不是 CSS 缩小。正式导出保持默认源尺寸及原收据序列化。

应用用例通过现有 RenderSubmission.video 端口提交两秒区间的画面 Job，CLI／HTTP／MCP／SDK／UI 共用 `opencut_visual_preview_cache_prepare`。完整固定快照、全局时间、尺寸／帧率／质量及实际执行器身份参与缓存键。身份包含 Native、Node、Chromium、FFmpeg／FFprobe 和执行包相关字节，不能用修订或 FFmpeg 哈希代替。精确帧网格由 Rust 返回，浏览器不重新求值工程。现有原子发布、取消、attempt、存储准入、owner／lease／generation／overlay 围栏继续生效。失败／取消任务按终态收据生成确定的替代请求，避免永久污染同内容缓存。

复杂海南段还暴露了 Mediabunny 预读跨越原生帧完成边界的问题。执行器现于帧末暂停新读取、排空已经发出的回调，再发送 frameComplete；下一帧恢复。源身份先验证，失效源不能带着停放请求进入下一帧。没有放宽原生协议或添加延时猜测。

最终缓存像素在原图片 Worker 内通过 OffscreenCanvas 绘制，不再让页面主线程负责每帧呈现。声音仍只有一个 AudioContext／Worklet：两端接收同一份实际量子区间，并使用同一 PreviewOutputClock 算法及设备输出时间投影。Worker 不拥有独立播放时钟，不按定时器累计工程进度；投影过期或没有已复制声音时保持位置。首帧及有界队列准备好才交接 PCM。两解码器、八帧队列、64 MiB 编码驻留及迟到丢弃界限保持有界，替换与关闭释放端口／位图／解码器。线程崩溃会停止相应播放并报告，不能静默留住旧画面。

页面将连续播放头与编辑状态订阅分开；时间显示／播放头局部刷新，编辑面板不随每个声音量子重建。人工编辑／打点仍读取实际输出位置。暂停、跳转、授权和修订变化保留原语义。额外修正了片尾编辑后失去 ended 会话，点击播放误提交终点的问题；起播请求按当前场景精确导航边界选择零点，仍由应用验证。

没有增加 crate、第三方依赖或架构例外。新增 Web 私有协议只承载现有类型、时钟事实与画布所有权；公共 DTO 继续从 Rust 生成。

较早同一呈现切片的海南全段也为 1050 帧、零漏帧；最终候选单独重跑，没有用旧运行替代。指标来自绘制提交与已建模设备输出，不能证明每个像素的物理扫描时刻。页面主线程最终一轮仍有 102.5 ms 的 rAF 间隙，而预览 Worker 最长换帧仅 52.17 ms，说明最终绘制已经隔离该停顿。

首次海南原生缓存从任务创建到全部发布为 **463 秒（7 分 43 秒）**。当前工程已预备完成；这不是即点即播或冷启动性能通过的声明。暂停／跳转仅在重新授权并核对相同清单／Job 身份后复用已校验字节。
